# 阶段 7: 端到端项目 (`07_project/`)

**目标**: 综合运用阶段 1-6 的全部知识，构建两个能跑通的端到端 Agent 应用。

前六个阶段我们一块一块地打磨"零件"：LLM 调用、工具、Agent 模式、框架、协议、多 Agent 协作。这一阶段把这些零件**组装成完整的机器**——两个各有侧重的实战项目。

---

## 项目 A: 研究助手 (`research_agent/`)

输入一个研究主题，自动产出一份结构化研究报告。

```
用户输入研究主题
    → ① 规划搜索策略      (Plan,     阶段 3)
    → ② 多子问题并行检索  (Tools +   阶段 2 / 多 Agent 分工 阶段 6)
    → ③ 信息整合分析      (综合,     阶段 1 结构化输出)
    → ④ 反思打磨报告      (Reflection, 阶段 3)
    → 输出结构化报告
```

| 文件 | 职责 |
|------|------|
| `schemas.py` | 各阶段间流动的强类型数据契约 (Pydantic) |
| `tools.py` | 工具层：网页搜索 (Bing) |
| `agents.py` | 四个专职 Agent：Planner / Researcher / Synthesizer / Critic |
| `main.py` | 编排流水线 + 演示入口 |

```bash
python 07_project/research_agent/main.py
```

## 项目 B: 代码助手 (`code_agent/`)

输入一句自然语言需求，自动产出**经过测试验证**的代码。

```
用户描述需求
    → ① 规划：定签名 + 测试用例  (Plan,       阶段 3)
    → ② 编码：生成实现          (Action,     阶段 3)
    → ③ 执行测试 (子进程沙箱)   (Tool,       阶段 2)
    → ④ 反思修复：带报错重写    (Reflection Loop, 阶段 3)
    → 输出最终代码
```

| 文件 | 职责 |
|------|------|
| `schemas.py` | 计划 / 代码 / 测试报告的数据模型 |
| `sandbox.py` | 代码执行沙箱：子进程 + 超时 + 客观测试结果 |
| `agents.py` | 两个 Agent：Planner (定契约) / Coder (写码&修复) |
| `main.py` | 编排"生成-测试-修复"闭环 + 演示入口 |

```bash
python 07_project/code_agent/main.py
```

---

## 两个项目的关键对比

| 维度 | 研究助手 | 代码助手 |
|------|---------|---------|
| 核心工具 | 网页搜索 | 代码执行沙箱 |
| 反思信号 | **主观**：Critic 打分判断"够不够好" | **客观**：测试是否全绿 |
| 收敛方式 | 达标或到最大轮数 | 测试通过或到最大修复次数 |
| 侧重点 | 多 Agent 分工 + 信息整合 | 生成-验证-自愈闭环 |

最值得体会的一点：**代码助手的反思有客观的收敛信号（测试通过），而研究助手只能靠 LLM 主观判断**。凡是能给 Agent 一个客观、可自动检验的目标，Agent 的可靠性就会大幅提升——这是设计 Agent 系统时最该争取的东西。

## 环境准备

```bash
pip install -e .            # 安装依赖 (httpx / beautifulsoup4 / pydantic 等)
cp .env.example .env        # 配置 OPENAI_API_KEY (兼容 API 还需设 OPENAI_BASE_URL)
```

> 研究助手依赖网络搜索；若网络不可用，搜索会优雅降级，流水线仍能跑通，只是报告质量下降。
