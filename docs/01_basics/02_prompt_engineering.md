## 核心概念

### 什么是提示词工程？

提示词工程 (Prompt Engineering) 是通过精心设计输入文本来引导模型输出的技术。它不需要修改模型本身，仅通过"怎么问"来改变"怎么答"。

```
普通提问: "帮我看看这段代码"
     ↓ 输出质量不可控

工程化提示: 角色 + 约束 + 格式 + 示例
     ↓ 输出稳定、可预期
```

### 四大核心技巧

| 技巧 | 核心思想 | 适用场景 |
|------|----------|----------|
| System Prompt 设计 | 定义角色、能力、约束、格式 | 所有场景的基础 |
| Few-shot | 通过示例"教"模型 | 格式化输出、分类任务 |
| Chain-of-Thought | 要求逐步推理 | 数学、逻辑、复杂分析 |
| Agent Prompt | 定义工具 + 流程 + 协议 | Agent 系统 |

## 四个示例详解

### 示例 1：System Prompt 设计

一个好的 System Prompt 应包含四个要素：

```
┌─────────────────────────────────────┐
│  角色 (Role)     → 你是谁？          │
│  能力 (Ability)  → 你能做什么？       │
│  约束 (Rules)    → 你不能做什么？     │
│  格式 (Format)   → 你怎么输出？       │
└─────────────────────────────────────┘
```

**代码中的实践：**

```python
system_prompt = """你是一个专业的代码审查助手。

## 角色
你是一位有10年经验的 Python 高级工程师。

## 能力
- 识别代码中的 bug、性能问题和安全漏洞
- 提供具体的改进建议和示例代码

## 约束
- 只关注最重要的 3 个问题，不要面面俱到
- 每个问题必须给出修复代码
- 语气专业但友好

## 输出格式
**问题 N**: [问题描述]
**严重性**: 高/中/低
**修复**: [代码示例]
"""
```

**设计要点：**
- 角色越具体，输出越专业（"10年经验的 Python 工程师" > "编程助手"）
- 约束比能力更重要 — 告诉模型"不要做什么"往往比"要做什么"更有效
- 明确输出格式可以大幅减少后处理工作

### 示例 2：Few-shot 提示

通过在对话中插入"示范问答对"，让模型模仿你期望的输出模式：

```python
messages = [
    {"role": "system", "content": "将情感分类为: 正面/负面/中性。只输出分类结果。"},
    # ---- Few-shot 示例 ----
    {"role": "user", "content": "这个产品太棒了，物超所值！"},
    {"role": "assistant", "content": "正面"},
    {"role": "user", "content": "发货速度一般般吧"},
    {"role": "assistant", "content": "中性"},
    {"role": "user", "content": "质量太差了，用了一天就坏了"},
    {"role": "assistant", "content": "负面"},
    # ---- 实际输入 ----
    {"role": "user", "content": "代码跑通了，虽然花了点时间但结果不错"},
]
```

**工作原理：**

```
Zero-shot:  指令 → 模型猜测格式 → 输出不稳定
Few-shot:   指令 + 示例 → 模型模仿格式 → 输出一致
```

**使用建议：**
- 示例数量：2~5 个通常足够，覆盖各类别
- 示例应覆盖边界情况（如"中性"这种模糊类别）
- 分类任务搭配 `temperature=0` 保证结果一致性
- 示例的顺序可能影响输出（注意避免偏差）

### 示例 3：Chain-of-Thought 思维链

让模型"展示解题过程"，而非直接给答案：

```python
# 不用 CoT
"请回答：一个书架有3层，每层8本..."  →  可能直接算错

# 使用 CoT
"请一步一步思考，展示你的推理过程，最后给出答案。"  →  推理更准确
```

**为什么 CoT 有效？**

```
直接回答: 问题 ──────────────► 答案 (一步到位，容易出错)

思维链:   问题 → 步骤1 → 步骤2 → 步骤3 → 答案 (分步推理，错误可追溯)
```

- LLM 本质是"逐 token 生成"，每一步推理都为下一步提供了"草稿纸"
- 复杂问题分解为简单步骤后，每步的出错概率大幅降低
- 推理过程可见，便于人类验证和纠错

**常用 CoT 触发短语：**
- "请一步一步思考"
- "让我们逐步分析"
- "先列出已知条件，再推导结论"
- "展示你的推理过程"

> 💡 CoT 是 ReAct Agent（推理 + 行动）的思想基础 — Agent 的"思考"步骤本质上就是 CoT。

### 示例 4：Agent 提示词设计

Agent 的 System Prompt 需要额外定义**工具**和**协议**：

```python
agent_prompt = """你是一个研究助手 Agent。

## 可用工具
1. search(query): 搜索互联网信息
2. calculate(expression): 计算数学表达式
3. summarize(text): 总结长文本

## 工作流程
1. 分析用户问题，确定需要哪些信息
2. 使用工具获取信息 (每次只调用一个工具)
3. 基于获取的信息回答问题
4. 如果信息不足，继续使用工具补充

## 输出规范
- 调用工具时: [TOOL: 工具名(参数)]
- 最终回答时: [ANSWER: 你的回答]
"""
```

**Agent Prompt 三要素：**

| 要素 | 作用 | 类比 |
|------|------|------|
| 工具定义 | 告诉 Agent 有哪些能力 | 给员工的"工具清单" |
| 工作流程 | 规定思考和行动的步驟 | 给员工的"SOP 手册" |
| 输出协议 | 约定机器可解析的格式 | 给员工的"汇报模板" |

> 本示例仅展示提示词结构。实际的工具调用将在 `02_tool_calling` 模块中通过 API 原生 function calling 实现。

## 提示词设计清单

设计提示词时，可以按此清单自检：

- [ ] **角色明确** — 模型知道自己"是谁"
- [ ] **任务清晰** — 一次只做一件事
- [ ] **约束具体** — 数量、长度、风格有明确限制
- [ ] **格式定义** — 输出结构可预期、可解析
- [ ] **示例充分** — 复杂任务提供 Few-shot
- [ ] **推理引导** — 复杂逻辑要求 CoT
- [ ] **边界处理** — 告诉模型遇到不确定情况怎么办

## 常见问题

**Q: System Prompt 和 User Prompt 有什么区别？**
A: System Prompt 设定全局行为（角色、规则），对用户不可见；User Prompt 是具体任务输入。System 的优先级通常更高。

**Q: Few-shot 示例越多越好吗？**
A: 不是。过多示例会占用 token、增加成本，且可能引入噪声。2~5 个高质量示例通常最优。

**Q: CoT 会增加 token 消耗吗？**
A: 会。推理过程本身消耗输出 token，但能显著提高复杂任务的准确率，是值得的权衡。

**Q: 为什么 Agent 需要约定输出格式（如 `[TOOL: ...]`）？**
A: 程序需要解析模型的输出来决定下一步动作。没有固定格式，就无法可靠地提取工具调用信息。
